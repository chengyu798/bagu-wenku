## 导读

读完这篇，你知道上下文窗口里通常装了什么、为什么会「越聊越笨」，以及选择、压缩、隔离、缓存各自解决什么问题。前置知识：Agent Loop、提示词工程。

## 基础概念

- **上下文窗口**：模型一次能看到的 token 上限。
- **token**：模型处理文本的基本单位，成本和延迟通常按它计算。
- **注意力预算**：窗口内信息越多，每条信息分到的注意力越少。
- **上下文腐蚀（context rot）**：上下文越长，模型对细节的注意力越分散。
- **压缩（compaction）**：把长历史摘要成结论或结构化状态。
- **RAG**：按需检索外部知识并放入上下文。
- **子 Agent**：用独立上下文处理子任务，只把结论带回主上下文。

## 核心结论

上下文工程是决定「模型在每一步应该看到什么」的工程：在有限的上下文窗口里，选择相关信息、压缩历史、隔离干扰、安排顺序，并管理工具结果和记忆。提示词工程只优化其中一段文字，上下文工程优化的是整个信息流。

## 原理与机制

**上下文窗口是一份有限的注意力预算**，通常同时装着：

- 系统提示与行为规则；
- 工具定义（往往比想象中占得多）；
- 记忆与用户偏好；
- 检索到的文档、代码和工具结果；
- 对话历史与草稿本；
- 为输出预留的空间。

**四类核心操作：**

| 操作 | 目的 | 典型手段 |
| --- | --- | --- |
| 写入 | 把重要信息外化，减轻记忆负担 | scratchpad、任务状态、笔记文件 |
| 选择 | 只放当前需要的内容 | RAG、按需读取文件、工具结果裁剪 |
| 压缩 | 减少 token 占用 | 摘要、compact、结构化状态替代原文 |
| 隔离 | 防止无关信息污染 | 子 Agent、独立会话、分区上下文 |

**常用技巧：** 工具结果只保留关键字段；长文档先检索再读取；历史对话定期摘要；稳定前缀放前面以命中 prompt cache；把大任务拆给子 Agent，只把结论带回主上下文。

**常见失效模式：**

- **Lost in the middle**：关键信息放在长上下文中间容易被忽略。
- **Context rot**：上下文越长，模型对细节的注意力越分散。
- **干扰与投毒**：检索到的无关内容或恶意指令影响决策。
- **工具结果淹没**：一次大输出挤掉真正重要的状态。

**和提示词工程的区别：** 提示词工程关注「这一句话怎么写」；上下文工程关注「这一轮以及后续每一轮，模型看到的信息集合如何构造、更新和淘汰」。

## 具体案例

一个持续 3 小时的修 bug 会话：

- 前 40 轮对话被压缩成几条结论：「问题在缓存失效逻辑」「已排除网络和数据库」；
- 完整日志存到文件，只在需要时读取关键时间窗；
- 检索到的 2000 行文档只保留相关函数的签名和调用关系；
- 大范围代码搜索交给子 Agent，主上下文只接收 5 条候选位置。

这样既保留了决策所需的信息，又避免上下文被原始日志和无关文档淹没。

## 追问链

1. **上下文工程和 RAG 是什么关系？** RAG 是「选择」的一种手段，负责把外部知识按需取回；上下文工程还要决定什么时候取、取多少、放在哪里、何时丢弃。
2. **什么时候该用子 Agent？** 子任务会产生大量中间结果、会污染主上下文，或者可以并行探索时；主 Agent 只接收结构化结论。
3. **工具结果太长怎么办？** 优先让工具返回摘要和引用（文件路径、ID），需要细节时再读取；不要无条件把完整 JSON 或日志塞回去。
4. **为什么稳定前缀很重要？** 很多模型支持 prompt caching，把系统提示和工具定义放在前面并保持稳定，可以显著降低延迟和成本。

## 常见误区

- 「上下文越长越好」是错的；无关信息会稀释注意力，增加成本和出错概率。
- 上下文工程不是一次性的提示词设计，而是每一轮都要做的动态决策。

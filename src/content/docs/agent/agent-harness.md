## 导读

读完这篇，你能说清模型和 Harness 的分工，知道一个 Agent 产品需要哪些运行时模块，以及为什么同一个模型换一套 Harness 效果会差很多。前置知识：Agent Loop。

## 基础概念

- **模型（model）**：只负责根据上下文做决策，不负责执行和权限。
- **Harness**：模型之外，负责循环、上下文、工具、权限、状态和追踪的运行时。
- **工具注册表**：工具名称、参数 schema 和执行函数的集合。
- **沙箱（sandbox）**：限制文件、网络和系统访问的执行环境。
- **追踪（trace）**：每一步输入输出、工具调用、token 和耗时的记录。
- **框架 vs 运行时**：框架是开发时使用的库，Harness 是实际跑起来的那套实现。

## 核心结论

Harness 是模型之外、把一次普通的模型调用变成 Agent 的全部运行时基础设施：它负责控制循环、组装上下文、注册和执行工具、管理权限与沙箱、保存状态与记忆，并记录追踪与评测。可以概括为：**Agent = Model + Harness + Environment**。

## 原理与机制

**Harness 通常包含这些模块：**

| 模块 | 职责 |
| --- | --- |
| 循环控制 | 决定何时继续、何时停止、何时重试 |
| 上下文组装 | 系统提示、工具描述、历史、记忆、检索结果 |
| 工具注册与执行 | schema 管理、参数校验、超时、错误处理 |
| 权限与沙箱 | 文件/网络访问控制、危险操作确认 |
| 记忆与状态 | 会话状态、长期记忆、断点恢复 |
| 追踪与评测 | 每一步的输入输出、token、延迟、失败原因 |

**为什么重要：** 同一个模型，换一套 Harness，任务成功率可能差很多。模型能力在趋同，Harness 的工程质量——工具粒度、上下文策略、错误恢复、权限设计——才是产品差异化的来源。

**和框架的区别：**

- **框架**（LangGraph、OpenAI Agents SDK 等）提供抽象和组件，是开发时使用的库。
- **Harness** 是实际跑起来的那套运行时，可能基于框架实现，也可能自研。
- 用户感知到的是 Harness，不是框架。

**设计取舍：**

- 自主性 vs 可控性：工具越多越自由，越需要权限和确认。
- 上下文大小 vs 成本：全量历史简单但昂贵，压缩和检索更省但实现复杂。
- 工具粒度：太细导致调用次数多，太粗导致参数复杂、复用性差。

## 具体案例

用 Claude Code 修一个 bug 时，模型只负责决定「读哪个文件、改哪一行」；真正让它变成 Agent 的是 Harness：

- 在工作区执行搜索、编辑和测试；
- 校验文件路径与命令权限，拦截危险操作；
- 把测试输出、报错和 diff 回填给模型；
- 记录每一步的 token、耗时和工具结果。

把同一个模型接到一个没有工具、没有上下文管理、没有权限控制的脚本上，它只能聊天，不能稳定地完成修复。

## 追问链

1. **Harness 和 Agent 框架的区别？** 框架是开发库，Harness 是运行时实现；同一个框架可以搭出不同质量的 Harness。
2. **为什么说 Harness 决定产品上限？** 工具设计、上下文策略、错误恢复和权限控制直接影响任务成功率与安全性，模型只是其中一个变量。
3. **怎么评测一个 Harness？** 用端到端任务集测成功率、平均步数、token 成本、延迟和安全事件，而不是只看单轮回答质量。
4. **自研 Harness 还是用现成框架？** 先明确需要的控制点和可观测性；通用场景用成熟框架，差异化在工具链、权限或上下文策略时再自研关键部分。

## 常见误区

- 不要把 Harness 等同于「提示词模板」；它包含执行、权限、状态和追踪。
- 也不要把「用了某个框架」当成「有了 Harness」；框架只是材料，运行时仍需设计和调优。

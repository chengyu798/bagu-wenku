## 导读

读完这篇，你知道提示词的结构化写法、常用技巧和评估方法，以及它在 Agent 里与上下文工程的分工。前置知识：LLM 的基本调用。

## 基础概念

- **prompt**：提供给模型的输入文本。
- **system prompt**：定义角色、规则和输出约束的高优先级指令。
- **zero-shot / few-shot**：不给示例 / 给少量输入输出示例。
- **结构化输出**：用 JSON Schema 或固定模板约束返回格式。
- **eval**：一组测试输入和判定标准，用来回归提示词效果。
- **上下文工程**：管理整个上下文窗口，提示词工程是其中一部分。

## 核心结论

提示词工程是用清晰的任务描述、必要的背景、明确的约束、恰当的示例和确定的输出格式，让模型稳定地产生想要的结果。它的核心不是「话术」，而是减少歧义、提供可模仿的模式，并用评估集持续验证。

## 原理与机制

**一份好的提示词通常包含五块：**

1. **角色与任务**：你是谁、要完成什么，动词要具体。
2. **背景与上下文**：完成任务需要的事实、约束和输入数据。
3. **约束与边界**：不能做什么、必须遵守什么、遇到不确定时怎么办。
4. **示例**：少量高质量的输入输出对，展示格式和边界情况。
5. **输出格式**：JSON Schema、字段说明、长度限制或模板。

**常用技巧：**

| 技巧 | 作用 |
| --- | --- |
| 明确动词和成功标准 | 把「帮我看看」改成「找出所有空指针风险并给出修复建议」 |
| 分隔符 | 用 XML 标签、三引号或标题把指令和待处理内容分开 |
| Few-shot | 用少量示例固定格式、语气和边界判断 |
| 结构化输出 | 用 JSON Schema 或严格模式减少格式错误 |
| 分解任务 | 把复杂任务拆成若干可验证的子步骤 |
| 预填充 | 让模型从指定开头继续，例如先给出 `{` 或固定前缀 |
| 反向约束 | 明确禁止项，比只写正面要求更能减少跑偏 |

**在 Agent 场景里：**

- 系统提示不仅描述角色，还要定义循环策略：什么时候用工具、什么时候停止、失败怎么处理。
- 工具描述本身就是提示词，决定模型选不选、传什么参数。
- Skill 可以看作「带资源的提示词包」，把流程和脚本一起固化。
- 提示词工程是上下文工程的一部分；后者还要决定每一轮放什么、压缩什么、丢弃什么。

**评估驱动：** 维护一组有代表性的测试输入和判定标准，每次改提示词都跑回归，而不是凭感觉「好像变好了」。

## 具体案例

让模型写周报时，提示词可以这样组织：

- **角色**：你是后端工程师，向直属主管汇报。
- **背景**：本周完成订单服务拆分，修复 3 个 P1。
- **约束**：300 字以内，不写流水账，突出风险和下周计划。
- **示例**：给一份历史好周报。
- **格式**：进展 / 风险 / 下周计划三段。

再准备 10 条历史周报作为 eval 集，每次改提示词都跑一遍，比较结构完整度和事实准确率，而不是凭感觉判断。

## 追问链

1. **提示词工程会被上下文工程取代吗？** 不会，它是上下文工程的子集；上下文工程还管历史压缩、检索、工具结果和记忆。
2. **Few-shot 什么时候有效？** 当任务需要固定格式、边界判断或隐含规则时；示例要多样且覆盖边界，否则模型会过拟合示例。
3. **工具描述应该怎么写？** 说明「什么时候用」「参数含义」「返回什么」「失败会怎样」，避免和其他工具的描述重叠。
4. **提示词越长越好吗？** 不是。冗长会稀释关键指令、增加成本；把稳定规则放前面，把动态内容放后面，必要时拆成多轮或交给 Skill。

## 常见误区

- 只写「请认真思考」「你是专家」这类空话，没有提供可执行的标准和示例。
- 把互相冲突的规则堆在一起，模型只能在冲突中随机选择。
